# 計画とSprint文書の例

既存の正本・書式を使う。これは必要な場合だけ使う例で、見出しやfileの一括生成を求めない。
小変更には計画・契約を作らない。通常機能は次のような短い計画で足りる。

```markdown
## 今回の変更
- 目的と範囲: [利用者に何ができるようになるか]
- 既決事項と制約: [今回に必要なものだけ、詳細は該当仕様へ参照]
- 確認方法: [受け入れ条件と必要なチェック]
```

## 大きな開発の仕様索引

`docs/spec.md` 等の既存索引は、機能/業務領域と読む条件だけを短く示す。
必要な領域の仕様を作成・更新し、重要判断の理由と置換先を既存の判断記録へ残す。
product/features/constraints/domain/uiの定型一式やCONTEXT.mdを一括作成しない。
現在状態はオーケストレーターだけが一つの正本を更新する。

## Sprint契約

```markdown
# Sprint N: [テーマ]

- ゴール: [この単位で動く状態にすること]
- 範囲: [含む振る舞い、関連仕様への参照]
- 承認・制約: [有効なものだけ]

## 受け入れ条件と検証
- [利用者から見た具体的な挙動]
- [影響する既存挙動と必要な確認]
- 証拠形式: [コマンド入出力、実操作結果等、十分な証拠 (safe harbor)]

## 未解決事項
- [利用者が決める必要のある点。なければその旨]
```

契約はWhatと確認対象を示し、検証基盤の実装仕様は書かない。
目的・挙動・合格基準の実質変更は既存承認範囲を確認し、未承認部分だけ判断を求める。
意味不変の訂正は理由を記録して進める。未変更仕様や巨大な採点表を複製しない。

採点が必要なSprintでは既存rubricを使い、必要な基準・閾値・合格時の挙動例・証拠を記す。
通常機能に6軸表を新設しない。基準の追加や厳格化、未達の扱いは
[変更分類](scope.md)と[評価](evaluation.md)に従う。

## Patch

Sprintを使う規模の追加だけ `sprint-NNN-patch-PPP` を採番し、Base Sprint・理由・対象範囲を上の契約に添える。
今回差分の分類に従い、小変更をmicro契約へ自動変換しない。旧microや小数IDは履歴として保持できる。
修正の往復は元Sprint内。新しい採点基準を修理の名目で追加しない。
