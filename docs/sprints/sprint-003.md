# Sprint 003 — 自律実行と文書設計

- Type: main
- Risk: standard（plugin全体の指示挙動変更として独立評価を実施）
- 目的: 初回から堅い実装と目的・決定・現在地の継承を保ち、小変更の固定Loop負担を取り除く。
- 承認: 2026-09-12のユーザー実装依頼。製品方針は確定済み、可逆な実装判断・修理は委任済み。

## 範囲

1. 小変更 / 通常機能 / 高リスク / 大きく曖昧な開発を影響に応じて扱い、root guidance、role、Skill、templates、
   docs、必要なruntime / migrationと関連検査の現在形を整合させる。
2. 常設guidanceを短い境界と条件付き入口へ、stateを一つの更新可能な現在状態へ整理する。
3. 既存正本を利用し、領域別仕様への短い索引、判断確定時の仕様更新と置換履歴、必要時だけの履歴参照を案内する。
4. 既存資料を使う質問を統合し、今回必要な利用者判断が解決したら停止する。
5. preview可能な既存repo保守移行の実行手段を製品として追加する。初期化no-overwriteと区別する。
6. Agenticの必要検証と独立評価を完了後、正式手順でYasashiiへ順次反映し、下流検証まで実施する。

現行の詳しい要求は [features](../spec/features.md)、保護境界は [constraints](../spec/constraints.md)。
過去Sprintの固定versionや全3役ルールを本Sprintへ適用しない。

## 受け入れシナリオ

### AC-01 小さな挙動変更

合成の既存管理repoで、影響が狭く可逆な表示順 / 入力補助の修正を依頼する。
担当Agentが必要な確認と検証を選んで直接完了でき、micro契約、独立レビュー、3役 / 3文書を必須にしない。
行数、画面数、既存自動テストの有無だけで振り分けない。

### AC-02 通常機能と高リスク

通常機能追加では必要な短い計画から実装へ進み、完成時に独立レビューを行う。
同じ程度の差分でも、権限変更 / データ移行 / 本番重要操作なら既存承認境界と実行前確認・実行後検証を維持する。
承認済みの可逆な修理に同じ承認を聞き直さず、未承認の重要副作用を沈黙で承認しない。

### AC-03 長い履歴からの再開

大量の履歴を持つ合成repoのstateから、対象仕様 / codeと必要な直近証拠へ到達できる。
全Sprint / 全履歴の全文読取を要求しない。既存の異なる仕様配置を尊重し、定型文書を無条件に追加しない。
現在の未解決事項・承認・制約を維持し、実装済み / 検証済み / 配備済みと証拠の対象版を区別する。
stateを更新し、過去詳細を履歴へ保持する。行数・byte数は目安で停止ゲートではない。

### AC-04 資料を使う質問と停止

既存資料に既決事項、一つの重要な未決事項、委任済み実装詳細がある合成例を使う。
既知 / 今回変更 / 未決を整理し、推奨案を添えた重要質問だけを行う。
模擬回答で重要判断が解決したら停止し、確定内容を既存仕様と判断記録へ反映する。
全設計分岐を訪問せず、単発修正でgrillingを強制しない。明示的な深いgrillingは引き続き可能。
記事grill-with-docsと同梱grillingの実装・出典を混同しない。

### AC-05 保守移行の実動と保護

旧Harness指示、独自規則、dirty、未解決事項、長いstate履歴、既存参照を持つ合成repoを使う。
CLIのpreviewは書き換えず、変更範囲を示す。承認対象の適用で元履歴・独自規則・dirtyを保持し、
対象の旧指示残存、参照切れ、未解決事項脱落を確認できる。
安全に自動更新できない箇所は保持・報告し、移行完了と偽らない。preview後に対象が変わった場合も保護する。
初期化を別途実行して既存ファイルを上書きしないことを確認する。実消費側repoは移行しない。

### AC-06 回帰とdownstream

指定既存回帰と変更対象の検査を実行し、旧期待を承認済み方針へ必要に応じて更新する。
Agentic独立評価後に正式downstream手順を実行し、Yasashii固有branding / 配布識別を保った差分と必要回帰を確認する。
既存dirty・私有監査をcommitへ混ぜず、release / push / tag / installed更新を追加しない。

## 評価と引き渡し

[今回のrubric](../spec/rubric.md)の証拠で十分。独立Evaluatorは実物のコマンド / 入出力と配布指示を使い、
文字列一致だけに依存しない。再評価は差分と影響範囲に限定し、新しい懸念がなければ全検査を反復しない。

Generatorは変更・検証・対象版・残件をprogressへ、Evaluatorは独立実行と判定をfeedbackへ記録する。
state更新はorchestratorのみ。対象差分の必要な限定commitは `sprint-003` prefixを使う。
品質PASSと速度計測は分け、未計測の高速化率を主張しない。実装完了・検証完了・下流同期・未配備を区別して報告する。
